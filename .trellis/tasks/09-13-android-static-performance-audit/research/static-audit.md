# Android scroll and Hero frame-drop static audit

Date: 2026-09-13
Branch: `task/09-13-android-static-performance-audit`
Method: source inspection, `HEAD` versus worktree diff, pinned external source trees, Flutter analysis, and focused widget tests. No Android device or frame timeline was used.

## Conclusion first

The high-refresh switch is not the leading explanation. The user has confirmed that Android is normally running at 120 Hz, and the Android branch only requests a high-refresh mode in `main()` (`lib/main.dart:21-30`). The more plausible static explanation is a workload spike that exceeds the roughly 8.33 ms budget of a 120 Hz frame and makes the cadence visibly fall back toward 60 Hz.

The highest-priority suspects are a combination, not one isolated line:

1. The current worktree `PixivImage.decodeWidthFor()` multiplies feed width by the platform DPR without the `HEAD` implementation's `layoutWidth * 1.5` cap (`lib/app/pixiv_image.dart:159-169`; `HEAD` had the cap at the same function). On a high-DPR Android phone this can create substantially larger decoded bitmaps than the Windows path normally does.
2. `kFeedCacheExtent = 800` is applied to the shared feeds (`lib/app/widgets/feed/feed_grid.dart:9-13`; callers include recommended, ranking, new, search, history, and profile). It drives a variable-height `SliverMasonryGrid` to build and lay out children beyond the viewport while those children also resolve `PixivImage` providers.
3. The Hero path is already optimized in places (`RepaintBoundary`, endpoint caching), but each animation tick still runs an `AnimatedBuilder`, a dynamic `HeroRectClip`, and potentially render-tree/header measurement. It also runs beside a 300 ms route `SlideTransition` (`lib/app/motion/hero_transition.dart:35-99`, `101-157`, `274-354`; `lib/app/navigation/routes.dart:123-153`). This is a separate, higher-confidence explanation for occasional Hero drops.

These are static risk rankings, not device measurements. Without an Android profile trace we cannot say whether a particular observed frame is UI-thread build/layout, raster/texture upload, image decode, memory pressure, or SurfaceFlinger scheduling.

## What is already helping, and what is not the culprit

- Feed images set `fade: false` (`lib/app/pixiv_image.dart:84-90`). This avoids starting a 350 ms image fade ticker for every card entering during a fling. It is a mitigation, not a likely cause of the reported finger-scroll issue.
- `SmoothWheelScroll` explicitly returns a pass-through builder on non-desktop platforms (`lib/app/widgets/smooth_wheel_scroll.dart:142-157`). Its 240 ms pointer-wheel animation is desktop-only (`:63-78`, `:93-140`), so it does not animate Android finger swipes.
- `PipelineWarmup` schedules only three startup post-frame callbacks and paints two offscreen tiny images (`lib/app/startup_gate.dart:131-210`). It may affect startup or the first flight, but it cannot explain recurring feed swipes.
- `FlutterDisplayMode.setHighRefreshRate()` is called only on Android startup (`lib/main.dart:21-30`) and the user has independently confirmed high refresh is active. Treating this as the root cause would contradict the observed condition.

## Feed causal chain

The shared path is:

`touch scroll -> CustomScrollView -> remainingCacheExtent -> RenderSliverMasonryGrid -> FeedItemExtent/IllustCard build -> PixivImage.memCacheWidth -> ResizeImage/cache -> image decode and texture upload -> card clips/repaint boundaries`

The important interaction is that `SliverMasonryGrid` is not just a paint-time arrangement. Its layout algorithm advances and lays out children until the cache end, and the app deliberately sets that cache end 800 logical pixels ahead. The child builder then performs image-provider work. A larger Android decode target multiplies the cost of each cache miss. This is why the most useful future A/B test is not "change the refresh rate"; it is "hold the data and device constant, then vary decode cap and cache extent independently."

The package does use a `SliverChildBuilderDelegate` through `SliverMasonryGrid.count` (`flutter_staggered_grid_view-0.7.0/lib/src/widgets/sliver_masonry_grid.dart:30-56`), so child creation is lazy, but lazy does not mean only-visible: `remainingCacheExtent` defines the lazy range. The report therefore does not claim that all feed cards are built at once.

## Hero causal chain

The Hero has three distinct costs:

1. **Per-tick widget/compositing work:** `AnimatedBuilder` rebuilds the clip wrapper for every animation value; `HeroRectClip` marks paint when its global rectangle changes and calls `pushClipRect` (`lib/app/motion/hero_rect_clip.dart:26-68`).
2. **Endpoint discovery:** the first usable viewport rectangle is cached, but null measurements are not. The fallback can inspect `CustomScrollView` slivers and call a nested header builder on each invocation (`hero_transition.dart:101-157`, `330-353`).
3. **Concurrent motion:** the Hero overlay flies while the destination page is also translated by the router's `SlideTransition` for 300 ms. `RepaintBoundary` limits image subtree repainting, but it does not remove the dynamic clip or route composition.

This path is consistent with "Hero occasionally drops" even if the feed itself is otherwise stable. It is not evidence that the Hero code is always over budget; the profile trace must show whether raster or UI time is the limiting side.

The strongest cross-client convergence is therefore not "other clients use a particular widget." It is bounded work admission: decode to the display target, limit the amount of high-resolution work admitted ahead of the viewport, and defer or pause image requests during an active fling when the platform/library makes that practical.

## Recommended next verification order

These are future, device-dependent checks; none were run in this task.

1. **Decode-size A/B:** same APK/data/device, compare current width with the `HEAD` cap. Log actual `memCacheWidth`, image-cache bytes, codec completion, UI time, raster time, and texture upload spikes.
2. **Cache-window A/B:** hold decode policy constant and compare 250 px versus 800 px. Count child builds and provider resolutions while a fling is active. This isolates cache admission from bitmap size.
3. **Request admission:** test whether deferring non-visible image requests during active scrolling reduces UI/raster spikes without leaving visible cards blank after idle. Pix-EzViewer's pause/resume approach is a comparison, not a prescribed implementation.
4. **Memory pressure:** visit all recommendation tabs and several detail pages, then inspect image cache bytes, process memory, GC, and whether `_completedDecodes` grows without bound.
5. **Hero trace:** capture push/pop flights with the normal route slide and with reduced motion. Inspect the first frame separately from steady-state ticks, and check whether `_heroMeasuredViewport` returns null and triggers the fallback repeatedly.

Only after these measurements should a product change be selected. The smallest likely implementation sequence would be decode-size policy first, cache/request admission second, and Hero composition only if its trace identifies a separate bottleneck.
